Аптайм и версия PostgreSQL
Время работы без перезапуска. Первое что смотрят после инцидента.
SELECT now() - pg_postmaster_start_time() AS uptime, pg_postmaster_start_time() AS started_at, version() AS pg_version;
Пояснения по колонкам
uptime Интервал с момента старта. После аварийного рестарта будет маленьким.
started_at Точная дата и время старта — сравни с временем инцидента.
pg_version Полная строка версии PostgreSQL. Нужна при обращении в поддержку.
Параметры, изменённые относительно дефолтных
Быстрый аудит конфигурации — все параметры которые отличаются от значений по умолчанию.
SELECT name, setting, unit, boot_val AS default_value, source, sourcefile, sourceline, pending_restart FROM pg_settings WHERE source NOT IN ('default','override') ORDER BY source, name;
Пояснения по колонкам
setting Текущее значение параметра.
default_value Значение по умолчанию — для сравнения с текущим.
source Откуда взято значение: configuration-file, environment-variable, command-line и т.д.
pending_restart true — изменение применится только после рестарта сервера.▸ Применить без рестарта: SELECT pg_reload_conf();
Параметры, ожидающие рестарта
Только те настройки, которые уже изменены в конфиге, но ещё не вступили в силу.
SELECT name, setting AS new_value, unit, short_desc, sourcefile, sourceline FROM pg_settings WHERE pending_restart = true;
Пояснения по колонкам
name Имя параметра (напр. max_connections, shared_buffers).
new_value Значение которое применится после рестарта PostgreSQL.
sourcefile / sourceline Где именно в конфиге задан параметр.
Использование пула соединений (% от max)
Сколько процентов max_connections уже занято — быстрый healthcheck.
SELECT max_conn, used, res_for_super, max_conn - used - res_for_super AS available, round(100.0 * used / max_conn, 1) AS used_pct FROM (SELECT (SELECT setting::int FROM pg_settings WHERE name='max_connections') AS max_conn, (SELECT setting::int FROM pg_settings WHERE name='superuser_reserved_connections') AS res_for_super, count(*) AS used FROM pg_stat_activity) t;
Пояснения по колонкам
max_conn Максимально допустимое число соединений (max_connections).
used Текущее число открытых соединений всех типов.
res_for_super Слоты зарезервированные для суперюзера.
available Реально доступных слотов для обычных пользователей.
used_pct Процент заполнения. > 80% — срочно нужен пулер или увеличение лимита.▸ При > 200 соединениях без пулера CPU тратится на переключение контекста. Используй PgBouncer.
Подключения по базам и состояниям
Сводка соединений с группировкой по БД и состоянию. Сравнивай с max_connections.
SELECT datname, state, count(*) AS connections, count(*) FILTER (WHERE wait_event_type='Lock') AS waiting_lock, count(*) FILTER (WHERE wait_event_type='IO') AS waiting_io FROM pg_stat_activity WHERE datname IS NOT NULL GROUP BY datname, state ORDER BY connections DESC;
Пояснения по колонкам
state active — запрос выполняется; idle — простой; idle in transaction — транзакция открыта без запроса (опасно!).
connections Количество сессий в данном состоянии.
waiting_lock Сессии ожидающие снятия блокировки. > 0 — активные конфликты.▸ SELECT current_setting('max_connections');
Подключения по приложениям
Кто подключён, сколько соединений от каждого приложения и в каком состоянии.
SELECT application_name, usename, datname, state, count(*) AS connections, count(*) FILTER (WHERE wait_event_type='Lock') AS lock_waits, min(now()-backend_start) AS oldest_conn FROM pg_stat_activity WHERE pid <> pg_backend_pid() AND application_name IS NOT NULL GROUP BY application_name, usename, datname, state ORDER BY connections DESC LIMIT 30;
Пояснения по колонкам
application_name Имя приложения передаётся клиентом. Пустое = приложение не установило имя.
oldest_conn Самое старое соединение от этого приложения — помогает найти утечки.▸ Установить имя: SET application_name = 'my_app'; или в строке подключения: application_name=my_app
Статистика WAL PG 14+≤ PG 16
Объём WAL, количество записей и синхронизаций. Помогает оценить нагрузку на запись.
SELECT wal_records, wal_fpi, wal_bytes, pg_size_pretty(wal_bytes) AS wal_size_pretty, wal_buffers_full, wal_write, wal_sync, wal_write_time, wal_sync_time, stats_reset FROM pg_stat_wal;
Пояснения по колонкам
wal_bytes Суммарный объём сгенерированных WAL-данных с момента сброса статистики.
wal_fpi Full page images — записи полных страниц после checkpoint. Много = частые checkpoints или большой random_page_cost.
wal_write / wal_sync Количество физических записей и fsync WAL на диск.
wal_buffers_full Сколько раз WAL-буферы были заполнены и пришлось сбрасывать на диск вне плана.▸ PG 14-16. В PG 17 wal_write/wal_sync/wal_write_time/wal_sync_time удалены — см. карточку для PG 17+.
Статистика WAL PG 17+
Объём WAL, количество записей и буфер. В PG 17 wal_write/wal_sync перенесены в pg_stat_io.
SELECT wal_records, wal_fpi, wal_bytes, pg_size_pretty(wal_bytes) AS wal_size_pretty, wal_buffers_full, stats_reset FROM pg_stat_wal;
Пояснения по колонкам
wal_bytes Суммарный объём сгенерированных WAL-данных с момента сброса статистики.
wal_fpi Full page images — записи полных страниц после checkpoint. Много = частые checkpoints или большой random_page_cost.
wal_buffers_full Сколько раз WAL-буферы были заполнены и пришлось сбрасывать на диск вне плана.▸ PG 17+. Время записи/синхронизации WAL теперь в pg_stat_io (object='wal').
Статус архивирования WAL
Мониторинг архивирования WAL — провалы архивации приводят к накоплению файлов и заполнению диска.
SELECT archived_count, last_archived_wal, last_archived_time, failed_count, last_failed_wal, last_failed_time, now() - last_archived_time AS time_since_last_archive, stats_reset FROM pg_stat_archiver;
Пояснения по колонкам
archived_count Количество успешно заархивированных WAL файлов.
failed_count Количество неудачных попыток архивации. > 0 = проблема с archive_command.
last_failed_wal Имя последнего файла который не удалось заархивировать.
time_since_last_archive Время с последней успешной архивации. Большое значение = архивация остановилась.▸ При failed_count > 0: проверь archive_command в postgresql.conf и права доступа к папке архива.

Общая сводка по сессиям (дашборд)
Один запрос — полная картина состояния сервера прямо сейчас.
SELECT state, count(*) AS total, count(*) FILTER (WHERE wait_event_type='Lock') AS lock_waits, count(*) FILTER (WHERE wait_event_type='IO') AS io_waits, count(*) FILTER (WHERE wait_event_type='LWLock') AS lwlock_waits, count(*) FILTER (WHERE now()-xact_start > interval '1 min') AS long_xacts, count(*) FILTER (WHERE now()-xact_start > interval '5 min') AS very_long_xacts, min(now()-xact_start) AS oldest_xact FROM pg_stat_activity WHERE pid <> pg_backend_pid() AND state IS NOT NULL GROUP BY state ORDER BY total DESC;
Пояснения по колонкам
lock_waits / io_waits Сессии ждущие блокировки или диска. Норма — несколько, плохо — много.
very_long_xacts Транзакции живущие > 5 минут. > 0 — стоит разобраться.
oldest_xact Возраст самой старой транзакции. Большой — проверь top5_long_xact.
Топ-10 самых долгих активных запросов Блокировки
Первое что смотреть при жалобах на тормоза — какие запросы выполняются дольше всего прямо сейчас.
SELECT pid, usename, datname, client_addr, now()-query_start AS duration, wait_event_type, wait_event, left(query,120) AS query FROM pg_stat_activity WHERE state='active' AND pid <> pg_backend_pid() ORDER BY query_start ASC LIMIT 10;
Пояснения по колонкам
duration Время выполнения текущего запроса. Растёт — запрос завис или ждёт.
wait_event_type / wait_event Lock = ждёт блокировку. IO = ждёт диск. NULL = реально работает на CPU.▸ Для детального анализа: EXPLAIN (ANALYZE, BUFFERS) <query>;
Топ-10 запросов в ожидании блокировки Блокировки
Запросы которые прямо сейчас ждут снятия чужой блокировки.
SELECT a.pid, a.usename, a.datname, now()-a.query_start AS waiting_duration, a.wait_event_type, a.wait_event, left(a.query,100) AS waiting_query, pg_blocking_pids(a.pid) AS blocked_by FROM pg_stat_activity a WHERE a.wait_event_type='Lock' AND a.state='active' AND a.pid <> pg_backend_pid() ORDER BY a.query_start ASC LIMIT 10;
Пояснения по колонкам
waiting_duration Как долго запрос ждёт блокировку.
wait_event relation = ждёт таблицу; tuple = ждёт строку; transactionid = ждёт завершения транзакции.
blocked_by PID(ы) процессов-виновников.▸ SELECT pg_terminate_backend(<pid из blocked_by>);
Топ-10 самых старых транзакций (любое состояние)
Старейшие транзакции — мешают VACUUM, накапливают bloat, удерживают XID.
SELECT pid, usename, datname, client_addr, state, now()-xact_start AS xact_age, now()-query_start AS query_age, left(query,100) AS query FROM pg_stat_activity WHERE xact_start IS NOT NULL AND pid <> pg_backend_pid() ORDER BY xact_start ASC LIMIT 10;
Пояснения по колонкам
xact_age Полное время жизни транзакции. Старые транзакции — главная причина bloat.
state active = выполняет запрос; idle in transaction = ждёт следующий запрос.▸ Если xact_age > 1 часа — почти всегда проблема.
Топ-10 запросов, пишущих временные файлы Производительность
Запросы которым не хватило work_mem и они сбрасывают данные на диск. Медленно.
-- Требует pg_stat_statements. Запросы которым не хватило work_mem:
SELECT queryid, calls, temp_blks_written, temp_blks_read, round(temp_blks_written*8192/1024.0/1024.0,1) AS temp_mb, round(total_exec_time::numeric,1) AS total_ms, round(mean_exec_time::numeric,2) AS mean_ms, left(query,100) AS short_query FROM pg_stat_statements WHERE temp_blks_written > 0 ORDER BY temp_blks_written DESC LIMIT 10;
Пояснения по колонкам
temp_blks_written Блоков (по 8 КБ) записано во временные файлы. Большое = work_mem мал для сортировок/хешей этого запроса.
temp_mb Объём временных файлов в МБ — наглядная оценка нехватки work_mem.
mean_ms Среднее время запроса. Сброс на диск сильно его увеличивает.▸ Временно для сессии: SET work_mem = '256MB'; Сбросить статистику: SELECT pg_stat_statements_reset();
Все активные запросы и зависшие транзакции Блокировки
Главный запрос оперативного мониторинга: всё что выполняется или застряло в транзакции. Data Egret style.
SELECT (clock_timestamp()-xact_start)::interval(0) AS xact_age, (clock_timestamp()-query_start)::interval(0) AS query_age, (clock_timestamp()-state_change)::interval(0) AS change_age, pid, state, datname, usename, coalesce(wait_event_type='Lock', false) AS waiting, wait_event_type||'.'||wait_event AS wait_details, client_addr||':'||client_port AS client, left(query,100) AS query FROM pg_stat_activity WHERE clock_timestamp()-coalesce(xact_start,query_start) > '00:00:00.1'::interval AND pid <> pg_backend_pid() AND state <> 'idle' ORDER BY coalesce(xact_start,query_start);
Пояснения по колонкам
xact_age Возраст транзакции — самый важный показатель для VACUUM и bloat.
query_age Возраст текущего запроса.
change_age Время с последней смены состояния.
wait_details Тип и событие ожидания в формате тип.событие. '-' = не ждёт.▸ Минимальный порог 0.1 сек отфильтровывает мгновенные транзакции.

Граф блокировок: кто кого блокирует Блокировки
Полная цепочка блокировок — виновник и жертва в одном запросе. Используй pg_blocking_pids.
SELECT blocked.pid AS blocked_pid, blocked.usename AS blocked_user, now()-blocked.query_start AS wait_duration, left(blocked.query,80) AS blocked_query, blocking.pid AS blocking_pid, blocking.usename AS blocking_user, blocking.state AS blocking_state, left(blocking.query,80) AS blocking_query FROM pg_stat_activity AS blocked JOIN pg_stat_activity AS blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid)) WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0 ORDER BY wait_duration DESC;
Пояснения по колонкам
blocked_pid PID процесса-жертвы.
wait_duration Как долго жертва уже ждёт. Растёт — ситуация не разрешается сама.
blocking_pid PID виновника — его нужно завершить или дождаться COMMIT/ROLLBACK.
blocking_state idle = забытая открытая транзакция, можно безопасно завершить.▸ SELECT pg_terminate_backend(blocking_pid);
Все активные блокировки с деталями объекта Блокировки
Полная таблица блокировок: что именно заблокировано, режим, выдано ли, возраст.
SELECT a.datname, l.relation::regclass AS locked_object, l.transactionid, l.mode, l.granted, a.usename, left(a.query,60) AS query, a.query_start, age(now(),a.query_start) AS age, a.pid FROM pg_stat_activity a JOIN pg_locks l ON l.pid=a.pid ORDER BY a.query_start;
Пояснения по колонкам
locked_object Имя таблицы (relation::regclass) или NULL для транзакционных блокировок.
mode Режим блокировки. AccessExclusive (ALTER TABLE, DROP) конфликтует со всем.
granted true = блокировка выдана. false = ожидает получения блокировки.▸ Таблица совместимости режимов: https://www.postgresql.org/docs/current/explicit-locking.html
Только неполученные блокировки (что именно ждёт) Блокировки
Список объектов которые прямо сейчас ожидаются — быстро найти что именно заблокировало систему.
SELECT relation::regclass, locktype, mode, transactionid, pid FROM pg_locks WHERE NOT granted;
Пояснения по колонкам
relation Таблица или индекс, на который ожидается блокировка. NULL = транзакционная блокировка.
locktype Тип: relation, tuple, transactionid, virtualxid, extend, advisory.
mode Запрошенный режим блокировки.
pid PID процесса который ждёт.
Детали блокировок: что именно заблокировано Блокировки
Расширенная информация о блокировках с именем объекта, режимами и длительностью у обеих сторон.
SELECT COALESCE(l1.relation::regclass::text, l1.locktype) AS locked_item, w.wait_event_type AS waiting_ev_type, w.wait_event, left(w.query,60) AS waiting_query, l1.mode AS waiting_mode, now()-ws.xact_start AS waiting_xact_dur, now()-ws.query_start AS waiting_query_dur, w.pid AS waiting_pid, w.usename AS waiting_user, left(l.query,60) AS locking_query, l2.mode AS locking_mode, now()-ls.xact_start AS locking_xact_dur, l.pid AS locking_pid, l.usename AS locking_user, l.state AS locking_state FROM pg_stat_activity w JOIN pg_locks l1 ON w.pid=l1.pid AND NOT l1.granted JOIN pg_locks l2 ON (l1.transactionid=l2.transactionid AND l1.pid<>l2.pid) OR (l1.database=l2.database AND l1.relation=l2.relation AND l1.pid<>l2.pid) JOIN pg_stat_activity l ON l2.pid=l.pid JOIN pg_stat_activity ws ON ws.pid=w.pid JOIN pg_stat_activity ls ON ls.pid=l.pid WHERE w.wait_event IS NOT NULL AND w.wait_event_type IS NOT NULL ORDER BY l.query_start, w.query_start;
Пояснения по колонкам
locked_item Что заблокировано: имя таблицы или тип локки (transactionid, virtualxid и др.).
waiting_mode / locking_mode Режимы. AccessExclusive (ALTER TABLE, DROP) конфликтует со всем.
locking_state idle = забытая транзакция, безопасно завершить. active = виновник ещё работает.
Дерево блокировок с deadlock-цепочками Блокировки
Рекурсивный запрос: полное дерево ожиданий с ролями процессов. ROOT BLOCKER — кого завершать.
WITH RECURSIVE l AS (SELECT pid, locktype, granted, array_position(ARRAY['AccessShare','RowShare','RowExclusive','ShareUpdateExclusive','Share','ShareRowExclusive','Exclusive','AccessExclusive'],left(mode,-4)) AS m, ROW(locktype,database,relation,page,tuple,virtualxid,transactionid,classid,objid,objsubid) AS obj FROM pg_locks), pairs AS (SELECT w.pid AS waiter, l.pid AS locker, l.obj, l.m FROM l w JOIN l ON NOT l.obj IS DISTINCT FROM w.obj AND l.locktype=w.locktype AND NOT l.pid=w.pid AND l.granted WHERE NOT w.granted AND NOT EXISTS (SELECT FROM l i WHERE i.pid=l.pid AND i.locktype=l.locktype AND NOT i.obj IS DISTINCT FROM l.obj AND i.m>l.m)), leads AS (SELECT locker, 1 AS lvl, count(*) AS q, ARRAY[locker] AS track, false AS cycle FROM pairs GROUP BY locker UNION ALL SELECT i.locker, leads.lvl+1, (SELECT count(*) FROM pairs q WHERE q.locker=i.locker), leads.track||i.locker, i.locker=ANY(leads.track) FROM pairs i, leads WHERE i.waiter=leads.locker AND NOT leads.cycle), tree AS (SELECT locker AS pid, locker AS dad, locker AS root, CASE WHEN cycle THEN track ELSE NULL::int[] END AS dl, NULL::record AS obj, 0 AS lvl, locker::text AS path, array_agg(locker) OVER () AS all_pids FROM leads o WHERE (cycle AND NOT EXISTS (SELECT FROM leads i WHERE i.locker=ANY(o.track) AND (i.lvl>o.lvl OR i.q<o.q))) OR (NOT cycle AND NOT EXISTS (SELECT FROM pairs WHERE waiter=o.locker) AND NOT EXISTS (SELECT FROM leads i WHERE i.locker=o.locker AND i.lvl<o.lvl)) UNION ALL SELECT w.waiter, tree.pid, tree.root, CASE WHEN w.waiter=ANY(tree.dl) THEN tree.dl ELSE NULL::int[] END, w.obj, tree.lvl+1, tree.path||'.'||w.waiter, tree.all_pids||array_agg(w.waiter) OVER () FROM tree JOIN pairs w ON tree.pid=w.locker AND NOT (w.waiter=ANY(tree.all_pids))) SELECT (clock_timestamp()-a.xact_start)::interval(0) AS xact_age, (clock_timestamp()-a.state_change)::interval(0) AS state_age, a.datname, a.usename, a.client_addr, tree.pid, replace(a.state,'idle in transaction','idletx') AS state, CASE WHEN tree.pid=ANY(tree.dl) THEN '!! DEADLOCK' WHEN tree.lvl=0 THEN 'ROOT BLOCKER' WHEN (SELECT count(*) FROM tree p WHERE p.path~('^'||tree.path) AND p.path<>tree.path)>0 THEN 'MID BLOCKER' ELSE 'VICTIM' END AS role, (SELECT count(*) FROM tree p WHERE p.path~('^'||tree.path) AND p.path<>tree.path) AS blocks_n, (CASE WHEN tree.pid=ANY(tree.dl) THEN '!> ' ELSE repeat(' . ',tree.lvl)||' ' END)||trim(left(regexp_replace(a.query,'s+',' ','g'),100)) AS query FROM tree LEFT JOIN pairs w ON w.waiter=tree.pid AND w.locker=tree.dad JOIN pg_stat_activity a USING (pid) JOIN pg_stat_activity r ON r.pid=tree.root ORDER BY (now()-r.xact_start), tree.path;
Пояснения по колонкам
xact_age Время жизни транзакции. У ROOT BLOCKER — самый старый.

query Запрос с отступами по уровню. Завершать — ROOT BLOCKER.▸ Deadlock PostgreSQL разрывает автоматически через deadlock_timeout (по умолчанию 1s).

set -e

PG_VERSION=17
PGDATA="/var/lib/postgresql/${PG_VERSION}/main"

PRIMARY_HOST="172.17.47.12"
PRIMARY_PORT="5432"

REPL_USER="repl"

echo "Stopping PostgreSQL..."
systemctl stop postgresql

echo "Cleaning PGDATA..."
rm -rf ${PGDATA:?}/*

echo "Starting basebackup..."

sudo -u postgres pg_basebackup -h ${PRIMARY_HOST} -p ${PRIMARY_PORT} -U ${REPL_USER} -D ${PGDATA} -Fp -Xs -P -R

echo "Fixing permissions..."
chown -R postgres:postgres ${PGDATA}
chmod 700 ${PGDATA}

echo "Starting PostgreSQL..."
systemctl start postgresql

echo "Checking replica status..."
sudo -u postgres psql -c "select pg_is_in_recovery();"

echo "Done."

from cte
where i_ratio > 100
order by i_ratio desc

Bloat индексов (точный расчёт, Josh Berkus) VACUUM
Точная оценка раздутия btree-индексов. Показывает только реально раздутые: >50% bloat и >50 МБ потерь.
-- Bloat таблиц и индексов (Josh Berkus). Показывает только реально раздутые.
WITH btree_index_atts AS (
    SELECT nspname, relname, reltuples, relpages, indrelid, relam,
        regexp_split_to_table(indkey::text, ' ')::smallint AS attnum,
        indexrelid as index_oid
    FROM pg_index
    JOIN pg_class ON pg_class.oid=pg_index.indexrelid
    JOIN pg_namespace ON pg_namespace.oid = pg_class.relnamespace
    JOIN pg_am ON pg_class.relam = pg_am.oid
    WHERE pg_am.amname = 'btree' ),
index_item_sizes AS (
    SELECT i.nspname, i.relname, i.reltuples, i.relpages, i.relam,
    s.starelid, a.attrelid AS table_oid, index_oid,
    current_setting('block_size')::numeric AS bs,
    CASE WHEN version() ~ 'mingw32' OR version() ~ '64-bit' THEN 8 ELSE 4 END AS maxalign,
    24 AS pagehdr,
    CASE WHEN max(coalesce(s.stanullfrac,0)) = 0 THEN 2 ELSE 6 END AS index_tuple_hdr,
    sum( (1-coalesce(s.stanullfrac, 0)) * coalesce(s.stawidth, 2048) ) AS nulldatawidth
    FROM pg_attribute AS a
    JOIN pg_statistic AS s ON s.starelid=a.attrelid AND s.staattnum = a.attnum
    JOIN btree_index_atts AS i ON i.indrelid = a.attrelid AND a.attnum = i.attnum
    WHERE a.attnum > 0
    GROUP BY 1,2,3,4,5,6,7,8,9 ),
index_aligned AS (
    SELECT maxalign, bs, nspname, relname AS index_name, reltuples,
        relpages, relam, table_oid, index_oid,
      ( 2 + maxalign - CASE WHEN 2%maxalign = 0 THEN maxalign ELSE 2%maxalign END
        + nulldatawidth + maxalign - CASE WHEN nulldatawidth::integer%maxalign = 0 THEN maxalign ELSE nulldatawidth::integer%maxalign END
      )::numeric AS nulldatahdrwidth, pagehdr
    FROM index_item_sizes AS s1 ),
otta_calc AS (
  SELECT bs, nspname, table_oid, index_oid, index_name, relpages, coalesce(
    ceil((reltuples*(4+nulldatahdrwidth))/(bs-pagehdr::float)) +
      CASE WHEN am.amname IN ('hash','btree') THEN 1 ELSE 0 END , 0 ) AS otta
  FROM index_aligned AS s2
    LEFT JOIN pg_am am ON s2.relam = am.oid ),
raw_bloat AS (
    SELECT current_database() as dbname, nspname, c.relname AS table_name, index_name,
        bs*(sub.relpages)::bigint AS totalbytes,
        CASE WHEN sub.relpages <= otta THEN 0 ELSE bs*(sub.relpages-otta)::bigint END AS wastedbytes,
        CASE WHEN sub.relpages <= otta THEN 0 ELSE bs*(sub.relpages-otta)::bigint * 100 / (bs*(sub.relpages)::bigint) END AS realbloat,
        pg_relation_size(sub.table_oid) as table_bytes,
        stat.idx_scan as index_scans
    FROM otta_calc AS sub
    JOIN pg_class AS c ON c.oid=sub.table_oid
    JOIN pg_stat_user_indexes AS stat ON sub.index_oid = stat.indexrelid )
SELECT dbname as database_name, nspname as schema_name, table_name, index_name,
        round(realbloat, 1) as bloat_pct,
        wastedbytes as bloat_bytes, pg_size_pretty(wastedbytes) as bloat_size,
        totalbytes as index_bytes, pg_size_pretty(totalbytes) as index_size,
        table_bytes, pg_size_pretty(table_bytes) as table_size,
        index_scans
FROM raw_bloat
WHERE ( realbloat > 50 and wastedbytes > 50000000 )
ORDER BY wastedbytes DESC;
Пояснения по колонкам
bloat_pct Процент раздутия индекса. >50% = индекс стоит перестроить (REINDEX CONCURRENTLY).
bloat_size Сколько места потеряно на раздутии этого индекса.
index_size / table_size Полный размер индекса и его таблицы — для оценки масштаба.
index_scans Сколько раз индекс использовался. 0 при большом bloat = кандидат на DROP, а не REINDEX.▸ REINDEX INDEX CONCURRENTLY schema.index_name; — перестройка без блокировки (PG 12+).

Cache hit ratio и статистика ошибок по БД
Главный показатель эффективности shared_buffers + rollback%, deadlocks, temp files.
SELECT datname, blks_read, blks_hit, round(100.0*blks_hit/NULLIF(blks_hit+blks_read,0),2) AS cache_hit_pct, xact_commit, xact_rollback, round(100.0*xact_rollback/NULLIF(xact_commit+xact_rollback,0),2) AS rollback_pct, deadlocks, temp_files, pg_size_pretty(temp_bytes) AS temp_size, stats_reset FROM pg_stat_database WHERE datname NOT IN ('template0','template1') ORDER BY blks_hit+blks_read DESC;
Пояснения по колонкам
cache_hit_pct % запросов из RAM. < 95% = shared_buffers мал или много cold reads.
rollback_pct % откатов. Высокий = много ошибок в приложении.
deadlocks Количество deadlock-ов. > 0 = проблема в логике приложения.
temp_size Размер временных файлов = work_mem мал. Увеличь work_mem.▸ Норма cache_hit_pct: > 99% для OLTP, > 95% для аналитики.
Профиль нагрузки: INSERT / UPDATE / DELETE
Соотношение операций записи по всему кластеру. Подсказывает характер нагрузки и стратегию тюнинга.
with s as (
    select
        sum(tup_inserted) as sum_i,
        sum(tup_updated) as sum_u,
        sum(tup_deleted) as sum_d,
        sum(tup_inserted)+sum(tup_updated)+sum(tup_deleted) as total,
        min(stats_reset) as reset
    from pg_stat_database
)
select
    total,
    100 * sum_i::bigint / greatest(total,1) as inserts_ratio,
    100 * sum_u::bigint / greatest(total,1) as updates_ratio,
    100 * sum_d::bigint / greatest(total,1) as deletes_ratio,
    now() - reset as stats_age
from s;
Пояснения по колонкам
inserts_ratio Доля INSERT. Высокая = append-нагрузка, важны fillfactor и партиционирование.
updates_ratio Доля UPDATE. Высокая = много dead tuples, критичен autovacuum и HOT-updates.
deletes_ratio Доля DELETE. Высокая = bloat, нужен агрессивный autovacuum или партиционирование с DROP.
stats_age Возраст статистики с последнего сброса. Чем больше, тем репрезентативнее картина.▸ Сбросить: SELECT pg_stat_reset(); — счётчики обнулятся для текущей БД.
Статистика bgwriter (PG < 17) ≤ PG 16
Эффективность буферного менеджера. Много buffers_backend = shared_buffers мал. Для PG < 17.
SELECT checkpoints_timed, checkpoints_req, round(100.0*checkpoints_req/NULLIF(checkpoints_timed+checkpoints_req,0),1) AS forced_pct, checkpoint_write_time, checkpoint_sync_time, buffers_checkpoint, buffers_clean, buffers_backend, round(100.0*buffers_backend/NULLIF(buffers_checkpoint+buffers_clean+buffers_backend,0),1) AS backend_write_pct, buffers_alloc, stats_reset FROM pg_stat_bgwriter;
Пояснения по колонкам
forced_pct % принудительных checkpoint. > 10% = нужно увеличить checkpoint_completion_target или max_wal_size.
buffers_backend Буферы записанные напрямую backend-процессами. Плохо — bgwriter не успевает.
backend_write_pct % записей через backend. > 10% = увеличь shared_buffers или bgwriter_lru_maxpages.▸ Сбросить: SELECT pg_stat_reset_shared('bgwriter'); Для PG 17+ используй pg_stat_checkpointer.

Установка PostgreSQL из PGDG (Ubuntu/Debian) ОС
Официальный репозиторий PGDG — всегда актуальные версии PG 12–18. Работает на Ubuntu 20.04/22.04/24.04 и Debian.
# 1. Установить зависимости
sudo apt install -y curl ca-certificates

# 2. Добавить ключ и репозиторий PGDG (автоматически определяет версию Ubuntu)
sudo install -d /usr/share/postgresql-common/pgdg
sudo curl -o /usr/share/postgresql-common/pgdg/apt.postgresql.org.asc   --fail https://www.postgresql.org/media/keys/ACCC4CF8.asc

sudo sh -c 'echo "deb [signed-by=/usr/share/postgresql-common/pgdg/apt.postgresql.org.asc]   https://apt.postgresql.org/pub/repos/apt $(lsb_release -cs)-pgdg main"   > /etc/apt/sources.list.d/pgdg.list'

# 3. Установить нужную версию (замени 17 на свою)
sudo apt update
sudo apt install -y postgresql-17 postgresql-client-17

# 4. Проверить статус
sudo systemctl status postgresql
sudo -u postgres psql -c "SELECT version();"
Пояснения по колонкам

postgresql-17 Замени 17 на нужную версию: 12, 13, 14, 15, 16, 17, 18.

-- local all       all                      md5

Ключевые параметры postgresql.conf
Минимальный набор настроек для production. Стартовые значения — ориентир, тюнинг под нагрузку.
-- Показать текущий файл конфигурации:
SHOW config_file;

-- Применить без рестарта:
SELECT pg_reload_conf();

-- Ключевые параметры (примеры значений для сервера с 32 GB RAM):
-- Memory
-- shared_buffers = 8GB          -- 25% RAM
-- work_mem = 64MB                -- осторожно: N соединений * sort_ops * work_mem
-- maintenance_work_mem = 1GB     -- для VACUUM, CREATE INDEX
-- effective_cache_size = 24GB    -- 75% RAM (подсказка планировщику)

-- WAL
-- wal_level = replica            -- минимум для репликации
-- max_wal_size = 4GB
-- checkpoint_completion_target = 0.9
-- wal_compression = on           -- PG 15+ поддерживает lz4, zstd

-- Connections
-- max_connections = 200          -- лучше пулер + меньше коннектов
-- superuser_reserved_connections = 5

-- Logging
-- log_min_duration_statement = 1000  -- логировать запросы > 1 сек
-- log_checkpoints = on
-- log_lock_waits = on
-- log_temp_files = 0             -- логировать все temp files

-- Statistics
-- track_io_timing = on           -- нужно для pg_stat_io (PG 16+)
-- shared_preload_libraries = 'pg_stat_statements'
Пояснения по колонкам
shared_buffers Самый важный параметр. 25% RAM — хорошая отправная точка.
work_mem Осторожно: умножай на max_connections * 3-5 = потенциальный пик RAM.
max_connections Лучше снизить до 50-100 и поставить PgBouncer перед PostgreSQL.
wal_compression PG 15+ поддерживает lz4/zstd. Значительно снижает объём WAL.▸ Калькулятор настроек: https://pgtune.leopard.in.ua/
Мажорный апгрейд pg_upgrade (общий алгоритм)
Алгоритм безопасного апгрейда PostgreSQL на новую мажорную версию через pg_upgrade.
-- 1. Проверка совместимости (без реального апгрейда):
/usr/pgsql-17/bin/pg_upgrade \
  -b /usr/pgsql-16/bin \
  -B /usr/pgsql-17/bin \
  -d /var/lib/pgsql/16/data \
  -D /var/lib/pgsql/17/data \
  --check

-- 2. Остановить старый кластер
sudo systemctl stop postgresql-16

-- 3. Инициализировать новый кластер
sudo /usr/pgsql-17/bin/postgresql-17-setup initdb

-- 4. Запустить pg_upgrade (--link = hard links, быстро)
sudo -u postgres /usr/pgsql-17/bin/pg_upgrade \
  -b /usr/pgsql-16/bin \
  -B /usr/pgsql-17/bin \
  -d /var/lib/pgsql/16/data \
  -D /var/lib/pgsql/17/data \
  --link --jobs=4

-- 5. Запустить новый кластер и обновить статистику
sudo systemctl start postgresql-17
sudo -u postgres /var/lib/pgsql/update_extensions.sh
sudo -u postgres vacuumdb --all --analyze-in-stages
Пояснения по колонкам
--check Проверка без изменений. Запускай всегда перед реальным апгрейдом.
--link Hard links вместо копирования — быстро, но старый кластер нельзя запустить.
--jobs Параллельные воркеры для конвертации файлов. = число CPU.
vacuumdb --analyze-in-stages Обязательно после апгрейда — восстанавливает статистику для планировщика.▸ Полный гайд: https://www.postgresql.org/docs/current/pgupgrade.html
Установка и настройка PgBouncer
PgBouncer — пулер соединений. Обязателен при > 50 коннектов к PostgreSQL.
# Ubuntu установка
sudo apt install -y pgbouncer

# RHEL установка
sudo dnf install -y pgbouncer

-- Минимальная конфигурация /etc/pgbouncer/pgbouncer.ini:
[databases]
myapp_db = host=127.0.0.1 port=5432 dbname=myapp_db

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction        ; transaction / session / statement
max_client_conn = 1000
default_pool_size = 20
reserve_pool_size = 5
log_connections = 0
log_disconnections = 0
server_tls_sslmode = require

-- Файл паролей /etc/pgbouncer/userlist.txt:
"myapp" "password_here"

-- Управление через psql:
psql -h 127.0.0.1 -p 6432 -U pgbouncer pgbouncer
SHOW pools;
SHOW stats;
SHOW clients;
Пояснения по колонкам
transaction mode Самый эффективный. Соединение с PG возвращается в пул после каждой транзакции.
session mode Соединение держится на время сессии клиента. Как без пулера.
max_client_conn Максимум клиентских соединений к PgBouncer (не к PostgreSQL!).
default_pool_size Количество реальных соединений к PostgreSQL на одну базу.▸ transaction mode несовместим с SET, prepared statements, LISTEN/NOTIFY.
Резервное копирование pg_basebackup
Физический бэкап через pg_basebackup. Основа для PITR и создания реплик.
# Полный бэкап с WAL (для PITR):
pg_basebackup \
  -h 127.0.0.1 -p 5432 -U repl \
  -D /backup/$(date +%Y%m%d) \
  -Ft -z \
  -Xs \
  -P -R

# Параметры:
# -Ft -z   — tar + gzip формат
# -Xs      — включить WAL в бэкап (stream)
# -P       — прогресс-бар
# -R       — создать standby.signal и recovery.conf для реплики

# Проверить размер бэкапа:
du -sh /backup/$(date +%Y%m%d)

-- Проверить права роли для бэкапа:
SELECT rolname, rolreplication, rolsuper FROM pg_roles WHERE rolname='repl';

-- Создать роль для бэкапа (минимальные права):
CREATE ROLE repl WITH REPLICATION LOGIN PASSWORD 'repl_password';
GRANT pg_read_all_settings TO repl;  -- PG 14+
Пояснения по колонкам
-Xs (stream) WAL стримится параллельно с бэкапом — гарантирует консистентный бэкап.
-R Создаёт standby.signal и postgresql.auto.conf с primary_conninfo — готово для реплики.
-Ft -z tar + gzip. Для параллельного сжатия: --compress=lz4 (PG 15+).▸ Для incremental backup: barman, pgbackrest, wal-g — см. их документацию.
Настройка логической репликации Репликация
Логическая репликация — репликация отдельных таблиц или баз. Работает между разными версиями PG.
-- НА ИЗДАТЕЛЕ (publisher):

-- 1. Установить wal_level = logical (требует рестарт):
ALTER SYSTEM SET wal_level = 'logical';
-- После рестарта проверить:
SHOW wal_level;

-- 2. Создать publication:
CREATE PUBLICATION mypub FOR TABLE orders, products;
-- Или для всей базы:
CREATE PUBLICATION mypub FOR ALL TABLES;

-- Проверить publications:
SELECT * FROM pg_publication;
SELECT * FROM pg_publication_tables;

-- НА ПОДПИСЧИКЕ (subscriber):

-- 3. Создать subscription:
CREATE SUBSCRIPTION mysub
  CONNECTION 'host=10.0.0.1 port=5432 user=repl password=xxx dbname=mydb'
  PUBLICATION mypub;

-- Проверить статус репликации:
SELECT * FROM pg_subscription;
SELECT * FROM pg_stat_subscription;

-- Мониторинг лага:
SELECT subname, received_lsn, latest_end_lsn,
  pg_wal_lsn_diff(latest_end_lsn, received_lsn) AS lag_bytes
FROM pg_stat_subscription;
Пояснения по колонкам
wal_level = logical Требует рестарт сервера. Нельзя снизить обратно до replica без рестарта.
pg_publication Список publication-ов на издателе.
pg_stat_subscription Статус подписок на подписчике — мониторинг отставания.▸ Логическая репликация поддерживает DDL только начиная с PG 15 (для некоторых операций).
Настройка потоковой репликации (шаги) Репликация
Физическая потоковая репликация — стандартный способ HA в PostgreSQL.
-- НА МАСТЕРЕ:

-- 1. Создать роль репликации:
CREATE ROLE repl WITH REPLICATION LOGIN PASSWORD 'repl_password';

-- 2. Добавить в pg_hba.conf:
-- host replication repl <replica_ip>/32 scram-sha-256
-- Перезагрузить:
SELECT pg_reload_conf();

-- 3. Установить параметры (postgresql.conf):
-- wal_level = replica
-- max_wal_senders = 5
-- wal_keep_size = 1GB    -- PG 13+, раньше: wal_keep_segments = 64

-- НА РЕПЛИКЕ:

-- 4. Остановить PostgreSQL на реплике
-- 5. Очистить PGDATA
-- 6. Запустить pg_basebackup с флагом -R:
pg_basebackup -h <master_ip> -p 5432 -U repl \
  -D $PGDATA -Fp -Xs -P -R

-- 7. Запустить PostgreSQL реплики
-- 8. Проверить репликацию:
SELECT * FROM pg_stat_replication;          -- на мастере
SELECT pg_is_in_recovery(), pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();  -- на реплике
Пояснения по колонкам
wal_keep_size PG 13+. Сколько WAL хранить для реплик которые временно отстали. Страховка.
-R (pg_basebackup) Создаёт standby.signal + primary_conninfo автоматически.
pg_is_in_recovery() true = это реплика, false = мастер.
Настройка SSL/TLS в PostgreSQL
Включение SSL для шифрования трафика между клиентом и PostgreSQL.
-- Проверить статус SSL:
SHOW ssl;
SELECT ssl, ssl_cipher FROM pg_stat_ssl WHERE pid = pg_backend_pid();

-- ssl = on

openssl req -new -x509 -days 365 -nodes \

chmod 600 /etc/postgresql/17/main/server.key

TCP-соединения к PostgreSQL (порт 5432) ОС
Количество и статусы соединений. Много TIME-WAIT = нет пулинга.
echo "=== States ===" && ss -tn '( dport = :5432 or sport = :5432 )' | awk '{print $1}' | sort | uniq -c | sort -rn && echo "" && echo "=== Top IPs ===" && ss -tn state established '( dport = :5432 or sport = :5432 )' | awk 'NR>1 {print $5}' | sed 's/:[0-9]*$//' | sort | uniq -c | sort -rn | head -15
Пояснения по колонкам
ESTAB Активные TCP-соединения.
TIME-WAIT Много = соединения пересоздаются слишком часто (нет пулинга).
CLOSE-WAIT Много = утечка соединений в приложении.▸ Решение: PgBouncer в transaction pooling mode.
Топ процессов по потреблению swap ОС
PostgreSQL в свопе = катастрофа. Найди виновника.
for pid in $(ls /proc | grep -E '^[0-9]+$'); do swap=$(awk '/VmSwap/{print $2}' /proc/$pid/status 2>/dev/null); name=$(awk '/Name/{print $2}' /proc/$pid/status 2>/dev/null); [ -n "$swap" ] && [ "$swap" -gt 0 ] && echo "$swap $name $pid"; done | sort -rn | head -10 | awk '{printf "PID: %-8s  Swap: %7s kB  Name: %s\n", $3, $1, $2}'
Пояснения по колонкам
Swap kB Объём swap. Если это postgres = запросы работают из свопа, в разы медленнее.
PID SELECT query FROM pg_stat_activity WHERE pid = <pid>;▸ vm.swappiness=1 — минимизирует использование swap.
